# OXC for TSRX 0.1.2

A feature release. Your own Oxlint JavaScript plugins now run on `.tsrx` files,
on the command line and in the editor, and one editor regression that came with
that work is fixed in the same release.

Nothing about ordinary `.js`, `.jsx`, `.ts`, and `.tsx` files changes. Native
Rust rules on `.tsrx` are unchanged. Formatting, the parser API, and the
language server's existing behaviour are unchanged.

## Your lint rules run on `.tsrx`

Up to 0.1.1, a `jsPlugins` entry in `.oxlintrc.json` made `oxlint` refuse the
whole run with:

```text
JavaScript plugins are not supported by the native TSRX path yet
```

That refusal is gone. Write an ordinary Oxlint plugin, register it the ordinary
way, and it reports on `.tsrx` files at the line and column of your authored
source:

```json
{
  "jsPlugins": ["./oxlint-demo-plugin.mjs"],
  "rules": {
    "tsrx-demo/no-banned-identifier": "error"
  }
}
```

There is no ESLint, no second linter, and no patched or unreleased OXC involved.
`oxlint` builds the legal-TSX projection it already builds for its native rules,
hands that to the published Oxlint binary so your rules run under Oxlint's own
plugin host, and maps every diagnostic span back to the bytes you wrote. Your
severities, rule options, `extends`, and `overrides` are resolved by Oxlint from
your own config, so a rule behaves on `.tsrx` the way it does anywhere else.

[The custom JavaScript plugins guide](../integrations/custom-js-plugins.md) is
the full description, including what your rule sees.

### It works in the editor too

The same rules appear as squiggles, at the same positions the command line
reports, through both the official OXC extension's multiplexer and the bundled
`oxc-tsrx-vscode` extension. The language server runs the lane on open, change,
and save, with a per-document cache keyed on the projection text, so a squiggle
never sits on bytes you did not write and never lingers after you fix the line.

### The cost: one extra parse per `.tsrx` file

Linting the projection means parsing it, so every `.tsrx` file that your plugins
run over is parsed one more time than it was in 0.1.1. This is never silent.
Each run that pays it prints one line to stderr, ahead of the report:

```text
oxlint (oxc-tsrx): running JS plugins on 1 .tsrx file(s) by linting the TSX
projection; this parses each of those files once more. Disable with
"settings": { "oxcTsrx": { "jsPluginsOnTsrx": false } }.
```

`--silent` suppresses it along with everything else. A `--format=json` report
carries the same fact as data, under `oxcTsrx.jsPluginProjection`, as
`{ "files": N, "extraParses": N }`, joined by `unmapped` in 0.1.3.

### Turning it off

If you would rather not pay the second parse, say so in `settings`:

```json
{
  "jsPlugins": ["./oxlint-demo-plugin.mjs"],
  "settings": {
    "oxcTsrx": { "jsPluginsOnTsrx": false }
  }
}
```

With that set, `oxlint` refuses a run that would have used your plugins on
`.tsrx` and exits 2 with the reason, and the editor publishes the same reason as
a diagnostic. It does not quietly run with your rules switched off. Your plugins
keep running on ordinary files either way.

### `context.filename` is the projection's path

Your rule is handed the projection, from a throwaway directory, so
`context.filename` ends in `.tsrx.tsx`: a `src/View.tsrx` in your project is
`<temporary directory>/src/View.tsrx.tsx` to your rule. The path relative to
your working directory is preserved, so a rule that tests for `src/` still
works, but one that compares against an absolute project path, or that expects
the extension to be `.tsrx`, does not. The diagnostic itself is still reported
against `src/View.tsrx`, which is what you and your editor see. The editor uses
a different throwaway directory per session.

### The Oxlint version this was built against

If the Oxlint your project resolves is outside `>=1.74.0 <2.0.0`, the command
refuses and exits 1 rather than running with your rules quietly switched off.

## The fix: a `jsPlugins` config no longer silences the editor

In 0.1.1, adding `jsPlugins` to `.oxlintrc.json` removed **every** diagnostic
from `.tsrx` files in the editor, native Rust rules included, with no error
anywhere. The Problems panel was simply empty.

The command line stripped `jsPlugins` before handing config to the native
engine, so it never met the capability gate. The language server did not strip
it, the engine refused, and the refusal was swallowed. The server now strips it
the same way, staging the rewritten config with your authored directory as the
config base so `extends`, `overrides` globs, and `ignorePatterns` still resolve
where they did.

The swallowing itself is fixed too, and for more than plugins. A lint session
the server cannot build no longer aborts silently: it publishes the reason as a
`lint-unavailable` diagnostic and logs it. A malformed `.oxlintrc.json` or two
conflicting config files now say so instead of showing you nothing. Formatting
stays available in that state.

## A whole-file rule now reports on `.tsrx`

A rule that reports on the whole `Program` fires at 1:1 on an ordinary `.tsx`.
On a `.tsrx` file it produced nothing at all, because its span covers the whole
projected source, markers and synthetic wrappers included, and no such span can
lie entirely inside text you wrote. A whole-file report has an obvious authored
position, so it is now mapped to your whole authored file and arrives at line 1,
column 1, the same place it lands on a `.tsx`.

A report whose span sits partly on a projection marker and partly on your own
code is still dropped, because a diagnostic at a position you did not write is
worse than no diagnostic. `oxc-tsrx lint --map-plugin-diagnostics` now returns
an `unmapped` count per file so that loss is countable rather than invisible.
The run itself still does not tell you. That is a known gap, and the plugins
guide says so where it describes what your rule sees.

## Upgrading

```bash
npm install oxc-tsrx@0.1.2
```

Nothing in your configuration has to change. If you previously moved `jsPlugins`
into an `overrides: [{ "files": ["**/*.tsx"] }]` block to keep the `.tsrx` half
of a mixed batch from failing the run, that workaround is no longer needed and
can be removed. It still works if you leave it.

## Known boundaries

The [limitations page](../reference/limitations.md) is the full list. The two
largest are unchanged: `.tsrx` is not buildable, and the type-aware lane needs
`oxlint-tsgolint` 0.24.0 and so does not work with the tsgolint that Vite+ 0.2.6
carries.

New in this release, and specific to the plugin lane:

- Your rule sees the projection, so TSRX control syntax has already been
  compiled away. `@if`, `@for`, `@switch`, and `@try` arrive as ordinary `if`,
  `for`, and `switch` statements, not as `JSXIfExpression` and friends. A rule
  that must see authored TSRX nodes needs the ESLint route described in the
  plugins guide.
- An `overrides` glob written for `.tsrx` is rewritten for you in the config
  that names `jsPlugins`, but not in a config reached through `extends`.
- The editor lane has not been exercised on Windows, where the language server
  spawns Node from a Rust process.

## Version-pin note for the maintainers

One pin in this repository deliberately still reads `0.1.1`: the root
`package.json` development dependency on `@oxc-tsrx/native-darwin-arm64`. That
is a dependency on a **published** artifact used as a local fixture, and 0.1.2
does not exist on the registry until this release is published. Move it, and
relock, after publication rather than before.
