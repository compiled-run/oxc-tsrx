# OXC for TSRX 0.1.4

A patch release. It makes a stock Vite+ scaffold able to lint `.tsrx` at all,
and it makes `oxc-tsrx setup` fix the editor rather than leaving it silently
dead.

## A stock `vp create` scaffold can now lint `.tsrx`

`vp create` writes `lint.options: { typeAware: true, typeCheck: true }` into
`vite.config.ts`. Either key on its own made `vp lint` exit 2 the moment one
`.tsrx` file entered the batch, reporting nothing:

```text
$ vp lint src
oxc-tsrx: type-aware tsgolint/type-check mode requires the explicit --type-aware
or --type-check opt-in; it is never started or silently disabled by config alone
EXIT=2
```

So the default scaffold could not lint this project's headline file type.

The cause was not the wrapper failing to forward the opt-in; it forwards it. The
native projection mode built a full lint session purely to reuse ignore rules,
and that tripped the type-aware gate. Emitting a projection is not evaluating
rules, so it is now exempt. A run that does evaluate rules is gated exactly as
before, and a plain `.oxlintrc.json` carrying the option still refuses.

```text
$ vp lint src
src/Greeting.tsrx:2:3: warning eslint(no-debugger): `debugger` statement is not allowed
src/Greeting.tsrx:3:9: error typescript(TS2322): Type 'string' is not assignable to type 'number'.
EXIT=1
```

Type-aware runs on `.tsrx` properly, at authored positions, so nothing had to be
degraded to get here.

## `setup` writes the one editor setting, and reports what it will not do

In a Vite+ project, `node_modules/.bin/oxlint` belongs to Vite+. That is where
the official OXC extension looks, so it found Vite+'s wrapper, which knows
nothing about `.tsrx`, and the editor showed no diagnostics with no error
explaining why.

`setup` now owns a fourth slot: `oxc.path.oxlint` in `.vscode/settings.json`,
written only when the `.bin` lookup does not already reach this package. It
merges one key and preserves comments and formatting, refuses to overwrite a
value you set yourself, and `remove` takes back exactly what it wrote. This is
the one file `setup` touches outside `node_modules`, and it says so on every run.

It also reports the TSRX editor prerequisites it deliberately does not own, and
names the tsconfig that actually owns your source rather than a solution-style
root where a plugin entry would be inert.

## Known boundary: Vite+ 0.2.6 and tsgolint

Vite+ 0.2.6 depends on `oxlint-tsgolint` 7.0.2001. This package pins 0.24.0 and
refuses any other version rather than running an unverified one.

| Vite+ | stock `lint.options`, batch contains `.tsrx` |
| --- | --- |
| 0.2.4 | works; type-aware runs on `.tsrx` |
| 0.2.6 | exits 2 with `unsupported tsgolint version 7.0.2001`; remove `lint.options` |

That is a version disagreement rather than a defect on either side, and it is
the one remaining reason a stock 0.2.6 scaffold needs an edit.

## Also

- The custom JavaScript plugin documentation is rewritten around the Oxlint
  route, with a walkthrough whose every command was executed on a fresh scaffold
  before publication.
- A claim that `@tsrx/typescript-plugin` "hangs silently on TypeScript 6" was
  removed. It does not reproduce: a stock scaffold on TypeScript 6.0.3 answered
  correctly three times out of three. What is true is only that the plugin
  declares `^5.9.3`, so a stock project sits outside its declared range.

## Known boundaries

Unchanged from 0.1.3, and the limitations page is the full list: `.tsrx` cannot
be built or bundled by this package, reports on projection-rewritten nodes are
dropped and counted, `context.filename` is the mirror path, each linted `.tsrx`
file is parsed once more, and Windows is published but the editor lane is
unexercised there.
