# OXC for TSRX 0.1.1

A patch release. It fixes one shipped defect that made a documented entry point
unusable, and corrects documentation that told you to run a command that could
not work.

## The fix: `oxc-tsrx/parser` now loads

Every 0.1.0 native package was published without its `parser.node` addon, so
importing the parser failed on every consumer machine and on every platform:

```text
ERR_TSRX_NATIVE_INTEGRITY
native package files: expected [...,"parser.node",...]; actual [...no parser.node...]
```

The addon was an optional input to the packaging script, the release never
passed it, and npm honoured the generated `files` list and left the addon out
of all eight tarballs. Nothing failed while building, so nothing caught it.

The command line was never affected. `oxlint`, `oxfmt`, and the language server
ship standalone executables under `bin/`, and those were packaged correctly in
0.1.0. Only the in-process parser API was broken.

If you use `import { parseSync } from "oxc-tsrx/parser"`, upgrade. If you only
use the commands, 0.1.0 already worked and this changes nothing for you.

### Why it cannot happen again

The packaging script now refuses to build a native package without the addon.
A package missing `parser.node` is rejected by the loader on install, so it was
never a shippable artifact, and it is no longer a buildable one. The release
job builds the addon for each target and passes it through.

The suite that covers this ran in no CI lane. It does now, and two real
breakages in it were repaired: it looked for a dependency at npm's hoisted
`node_modules` path, which pnpm does not create, and it installed with
`--offline` into an empty cache, which cannot resolve the packages it needs.

## Documentation corrections

- **`oxc-tsrx setup` is documented per package manager.** Every non-npm tab
  previously printed `npx oxc-tsrx setup`, which cannot run in a Vite+ project:
  `vp create` declares `devEngines.packageManager`, and npm exits with
  `EBADDEVENGINES` when that names a different manager. Use `pnpm exec`,
  `yarn`, or `bunx` instead. Corepack is never required, and any modern version
  of your package manager works.
- **Limitations now lead with the fact that `.tsrx` cannot be built or run.**
  There is no Vite, Rollup, or Rolldown plugin, and the legal-TSX projection
  stays inside Rust rather than coming back as source, so you cannot write one
  from the public API either. Importing a `.tsrx` module into an application
  fails in the bundler. This was true in 0.1.0 and was not written down.
- **The Vite+ page records three template defaults you have to turn off.** A
  project scaffolded by `vp create` enables `jsPlugins`, `options.typeAware`,
  and `options.typeCheck`, and the native TSRX path refuses all of them. Each
  one fails the whole run before any file is linted, including your ordinary
  `.tsx` files.

## Known boundaries

Unchanged from 0.1.0, and the limitations page is the full list. The largest
are that `.tsrx` is not buildable, that JavaScript lint plugins do not run
against `.tsrx`, and that the type-aware lane needs `oxlint-tsgolint` 0.24.0
and so does not work with the tsgolint that Vite+ 0.2.6 carries.
